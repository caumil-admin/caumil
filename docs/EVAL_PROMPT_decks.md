# EVAL_PROMPT_decks.md — 발표자료 평가 지침 (v5 심사 기준 4항목을 발표자료에 적용)

2026-10-23 부터 드라이브 발표자료 폴더(팀 10/26 · 개인 10/27)의 슬라이드(pptx·pdf)와 대본(hwpx)을 **원고와 같은 심사 기준**(`data/rubric.json`)으로 채점해 발표자료 기준 순위를 따로 매긴다(`pipeline/decks.py`). 원고 평가(`eval/`)는 그대로 두고, 발표자료 평가는 `eval_deck/<ID>.json` 에 쓴다. ID 는 주 원고 ID(`data/decks.json` 의 `id`, `papers` 의 첫 번째).
세션은 발표자료마다 아래 공통 지침 + 자료 정보(ID·파일·PDF 경로·다루는 원고·원고 점수)를 에이전트 1개에 주고 병렬로 돌린 뒤, 전 자료의 세부 요소를 한 표에 놓고 척도를 보정한다.

## 에이전트 지침(공통)

```
당신은 C:\Users\choi\Desktop\aice\caumil.io 저장소에서 경진대회 **발표자료 한 건**을 심사 기준 4항목(v5, data/rubric.json)으로 채점하는 평가자입니다.
결과물은 eval_deck/{ID}.json 한 파일뿐입니다. 다른 파일은 수정하지 말고 ./run.sh 나 pipeline 스크립트를 실행하지 마세요. 파이썬(python)은 JSON 검증용으로만 쓰세요.
개인 이메일 주소는 어떤 필드에도 적지 않고 '@' 문자를 쓰지 않습니다(mAP@50 은 'mAP50').

## 먼저 읽을 것
1. data/rubric.json — 4항목·세부 요소 12개의 정의와 0/0.5/1 앵커.
2. 발표자료 텍스트 source_text/decks/{ID}.txt — pptx 는 [슬라이드 n] 본문 + [노트] 발표자 노트, PDF 는 커넥터 텍스트(쪽 구분 없음), 대본(hwpx)은 발표 원고. 끝까지 읽으세요.
3. 슬라이드 화면(있으면) — 세션이 준 PDF 경로를 Read 도구로 pages 를 나눠(한 번에 20쪽 이하) 전부 보세요. 그림·표·배치·글자 크기·시각 위계는 텍스트에 없으므로 **화면으로 판단**합니다. 대본만 있는 자료는 화면 평가가 불가능하므로 why 에 그렇게 적습니다.
4. 다루는 원고의 평가 eval/{PID}.json(요약·점수·리스크)과 원고 전문 source_text/{PID}.txt — **발표자료 주장이 원고와 맞는지 확인하는 용도**입니다(수치·주장·범위 불일치 → consistency 에 적고 심하면 flags). 원고에만 있는 내용으로 발표자료 점수를 채우지 않습니다. 발표자료가 두 원고를 통합한 것이면(papers 가 2개) 두 원고 모두와 대조합니다.

## 채점 원칙
- 심사위원이 **발표자료만 보고** 얻을 수 있는 근거로 매깁니다. 슬라이드 본문·발표자 노트·화면·대본이 근거이고, 원고는 대조용입니다.
- 분량이 짧다고(5분·10분 발표) 그 자체를 감점하지 않습니다. 다만 근거가 자료에 없는 세부 요소는 낮게 줍니다. 10분 발표에 담길 수 있는 범위를 기준으로 '충분히 보였는가'를 봅니다.
- 세부 요소 0~1, 0.05 단위. 항목 score = 세부 평균(소수 둘째 자리, half up). 리스크는 점수에 넣지 않고 flags 에만.
- 척도(원고 지침 docs/EVAL_PROMPT_v5.md 와 같은 뜻, 발표자료용으로 읽는 법):
  [technical] validity — 기법 선택 근거와 그것이 동작함을 보이는 결과가 자료에 있는가(0.85 근거+결과 분명 / 0.65 결과는 있으나 선택 근거 일반적 / 0.5 방법 소개만 / 0.3 명목적). sustainability — 연산·데이터·운용 조건·배치 경로·한계를 자료가 다루는가(0.85 실기기·운용 조건까지 / 0.65 구현·검증 조건 일부 / 0.5 언급 없음에 가까움 / 0.3 설계만). understanding — 모델 동작·한계·설정 선택·실패 사례를 자료가 설명하는가(0.85 한계·실패 분석까지 / 0.65 설정·동작 설명 / 0.5 모델 이름·개념 수준 / 0.3 오류).
  [innovation] novelty — 자료가 무엇이 새로운지 분명히 세우는가(0.85 새 접근·문제 정의가 분명 / 0.65 의미 있는 개선·새 조합 / 0.5 적용 / 0.35 재현·벤치마크). valueProp — 기존 솔루션·기준선과의 차이를 수치·정성으로 보이는가(0.85 정량 비교 / 0.65 정성 비교 / 0.5 언급만 / 0.3 없음). creativeUse — 문제 구조에 맞춘 변형·결합이 드러나는가.
  [structure] flow — 문제→방법→결과→결론이 빈틈없이 이어지고 수치가 슬라이드 간·원고와 일치하는가(0.85 / 0.7 작은 비약 / 0.5~0.6 눈에 띄는 비약·불일치·템플릿 잔재). dataDriven — 데이터·설정·수치·통계가 자료에 구체적으로 제시되는가(0.85 조건·수치·출처 표기 / 0.65 주요 수치 / 0.5 일부 / 0.3 수치 없이 주장). market — 적용 대상·절차·효과·확장 경로가 구체적인가.
  [presentation] clarity — 슬라이드당 메시지 하나, 헤드라인 문장, 시각 위계·글자 밀도·가독성, 전문적 외관, 도입의 몰입 장치(0.85 몰입·명확·전문 모두 높음 / 0.65 명확하나 평이 / 0.5 글자 과밀·메시지 불명확이 섞임 / 0.3 전달 불명확). timing — 자료에 시간 배분 근거가 있는가: 노트의 슬라이드별 배정 시간 합이 발표 시간과 맞는지, 장수가 시간에 적절한지(10분에 10~20장, 5분에 6~12장을 기준으로 봄). 근거가 전혀 없으면 0.5 로 두고 why 에 "자료에 시간 배분 근거 없음(자리값)". qa — 발표 전이라 **항상 0.5**, why "발표 전 미평가(자리값)".
- 대본(hwpx)만 있는 자료: clarity 는 대본의 메시지·구조·쉬운 말 전환으로, timing 은 대본의 구간 시간 표기로 매기고 화면 요소는 평가 불가라고 적습니다.
- consistency: 발표자료의 수치·주장이 원고와 어긋나는 곳, 원고에 없는 주장(과장), 원고 핵심 결과의 누락을 적습니다. 자료가 원고와 다른 결과 수치를 쓰면 flags high.
- 흔한 리스크(flags): 실명·소속 노출이 심사 규정에 어긋날 가능성은 적지 않습니다(발표는 블라인드가 아님). 대신 출처 없는 그림·영상(저작권), 원고와 다른 수치, 템플릿·다른 과제 잔재(예: PDF 메타데이터 제목이 다른 과제), 재생 의존(영상이 안 나오면 빈 슬라이드), 글자 과밀을 봅니다.

## 출력 — eval_deck/{ID}.json (UTF-8, ensure_ascii 없이, 들여쓰기 1, 끝에 개행)
필드 순서: id, deckTitle(파일명), format(pptx|pdf|script), slides(장수, 대본은 null), durationMin(자료·파일명에 적힌 발표 시간, 없으면 null), papers(배열), summary(자료가 전하는 이야기 3~4문장), strengths(2~3문장), consistency(원고와의 일치 2~4문장), keyNumbers(자료에 나오는 대표 수치 3~4개), fixes(보완 우선순위 3개 — 발표자료 관점), flags([{level: high|mid, text}]), evidenceQuotes(source_text/decks/{ID}.txt 에 부분 문자열로 존재하는 문장 3~5개), rubric, evaluatedAt, textSha.
rubric = {technical|innovation|structure|presentation: {sub: {...}, score: 세부 평균(소수 둘째 자리, half up), why: 세부 요소마다 "라벨 점수: 근거(슬라이드 번호, 자료 속 수치)" 한 문단}, total, evaluatedAt}.
total = 100 × (technical 세부 평균 + innovation 세부 평균 + structure 세부 평균) ÷ 3, 소수 첫째 자리(기본 프리셋 '원고 3항목 균등' — 원고 순위와 같은 식이라 비교 가능. 발표 항목은 total 에 넣지 않음).
저장 뒤 파이썬으로 JSON 파싱, 0.05 격자, score·total 계산, evidenceQuotes 의 존재(substring), '@' 부재, textSha 일치(세션이 준 값)를 검사하고 고치세요.
마지막 보고는 짧게(10줄 안): 12개 세부 요소·4항목·total, 원고 점수와의 차이가 큰 항목과 이유 한 줄, high 리스크, 자료 성격 한 줄.
```

## 받은 뒤 할 일(세션)
1. 전 자료의 세부 요소를 한 표에 놓고 척도를 본다(같은 성격끼리 어긋나면 why 와 함께 고치고 "(척도 보정 M/D — 이유)" 를 남긴다). 같은 조·같은 저자의 두 자료는 나란히 본다.
2. `grep -l '@' eval_deck/*.json` 으로 이메일이 없는지 본다.
3. `PY=python ./run.sh decks score && PY=python ./run.sh decks check && PY=python ./run.sh decks report` → `dist/decks.html`(내부용, 배포·푸시 금지).
